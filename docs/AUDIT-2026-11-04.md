# Audit of 2026-11-04 — end of M2 (branch `m2`, 4e75382)

Scope: the broker, the fence and the tree, the release path, the installer and first-boot setup, and
the security claims against the tests, as in the audits of 2026-11-01. Read-only on the repository.
No VM tests were run. Evaluation harnesses and experiments are in the scratchpad (`main/`, `release/`,
`installer/`). Two parts were delegated to fresh reviewers: the release path, and the installer and
setup. Their key results were reproduced here: A1 and A2 were re-run, and A4 was checked against its
unit test.

## Verdict

**No high-severity hole was found.** The broker's trust boundary is what the documents say it is, no
better and no worse:
- a root broker takes its settings only from `/etc/torq/broker.json`;
- children get a cleared environment;
- every build is the ledgered commit (`git+file://…?rev=`);
- the lock covers the switch unit;
- interrupted operations are reconciled.

The weak points that remain are the ones KNOWN-GAPS already concedes: identity is caller-supplied
(#4/6a/6i), the ledger is unkeyed and can be truncated (#2), 6e, and N3.

The fence holds against everything tests/tree.nix covers. Three further spellings remove the
broker's own units (A7). Those are system-tier changes a person approves, but the README claims
"however they are spelled".

**The release path is the weak part of M2.** "A machine updates only to a commit signed with the
release key" is not true today, in three ways:
- the check accepts a commit signed with OpenPGP (A1);
- what Nix builds is decided by the lock's `narHash`, not the `rev` whose signature was checked (A2);
- `stable` can move to an older release with no warning, because the "downgrade" check compares CI
  commit dates (A3).

**One setup defect can leave a fresh install nobody can log in to** (A4).

**Recommendation:** fix A1, A4 and the CI side of A3 before `v0.2.0`, the first release real people
will install. Record A2 in 6c and ADR-028 as a stronger form of that gap; its fix belongs in the
broker with the M3 work. Everything else goes in the KNOWN-GAPS table.

## Findings

### A1 — medium — the release check accepts a gpg-signed (or X.509-signed) commit
- **Where:** `cli/src/release.rs:36` and `:50`.
- **What is wrong:** `git verify-commit` chooses its verifier from the signature's own header, not
  from `gpg.format`. A commit signed with OpenPGP is checked by `gpg` from the caller's PATH, against
  the caller's keyring (HOME and GNUPGHOME are inherited), and `gpg.ssh.allowedSignersFile` is never
  consulted. git counts a good signature from a key of unknown trust (`U`) as success. torqcli then
  prints the "Good signature…" line as "signed by the TorqOS release key".
- **Scenario:**
  1. Someone who can push to `torqos-releases` (a leaked `TORQOS_RELEASES_TOKEN`, see A5) puts a
     commit on `stable` signed with their own OpenPGP key.
  2. The person has gnupg installed, and that key in their keyring (imported, or fetched by gpg's
     `auto-key-retrieve`).
  3. The person runs `request system update`: the commit passes the check and is built as root.
  gnupg is not in the base, which keeps this from being high.
- **Verified:** yes. The release reviewer built a gpg-signed commit
  (`scratchpad/release/gpgtest2.sh`), and it was re-run here with exactly release.rs's git
  arguments: exit 0 with the key imported at unknown trust, exit 1 with an empty keyring.
- **Fix:**
  - Do not use `verify-commit`. Take the signature from `git cat-file commit`, require
    `-----BEGIN SSH SIGNATURE-----`, and run `ssh-keygen -Y verify -n git -I torqos-release -f
    /etc/torq/release-signers` from a fixed path.
  - At the least, set `gpg.openpgp.program` and `gpg.x509.program` to a program that always fails,
    and point HOME and GNUPGHOME at the temp folder.
  - Add a unit test with an OpenPGP-signed commit.

### A2 — medium — the signed `rev` is not what is built: the lock's `narHash` is
- **Where:**
  - `cli/src/session.rs:963-968` and `cli/src/software.rs:83-93` check only `locked.rev`;
  - `broker/src/config.rs:74-79` builds with `--no-update-lock-file` and checks nothing about the
    `torq` input.
- **What is wrong:** Nix looks a locked input up by its `narHash`. If a store path with that hash
  already exists, Nix uses it without fetching or comparing it with `rev`. A lock can therefore name
  a `rev` the release key signed while its `narHash` points at any source already in the store.
- **Scenario: a silent downgrade.** An older release's source is in the store by design:
  `lib.mkSystem` keeps each generation's sources in `system.extraDependencies`.
  1. A lock is written that holds the newest signed `rev` and the narHash of an older release's
     source. It could come from a hand-made `torq-broker propose` diff, or later from the agent.
  2. Every check that exists passes.
  3. The ledger records the new rev.
  4. The machine runs the old TorqOS.
  The person sees only a changed hash in a raw diff. KNOWN-GAPS 6c concedes that the person's own
  fetch shapes the narHash. This is worse: any lock not written by the approver's own update is
  unchecked, and moving the signature check into the broker would not close it.
- **Verified:** yes, reproduced here with Nix 2.34.9 (`scratchpad/release/nartest.sh`). A lock with a
  real `rev` and a planted `narHash` evaluates to the planted content.
- **Fix:** the broker, at apply, re-fetches every changed locked input as root:
  - for `torq`, from `torq.releases.url` at `rev`;
  - it recomputes the narHash and refuses a mismatch (6c's own fix, now required);
  - then it checks the SSH signature itself.
  Until then, say in ADR-028 and 6c that a lock someone else wrote is not covered.

### A3 — medium — `stable` can move backwards, and nothing on the machine says so
- **Where:**
  - `.github/workflows/release.yml:95-105`;
  - `cli/src/session.rs:1688-1692` and `cli/src/pkg.rs:120-133`;
  - ADR-028's Consequences.
- **What is wrong:** each release is a new commit on top of the releases repo's `main`, so pushing it
  to `stable` is always a fast-forward, whatever the version. "Forward only" means forward in git,
  not in version.
  - Machines compare inputs by `lastModified`, which is the CI commit's time, so a backport tag
    published after a newer release looks newer and gets no "downgrade" line.
  - Signed pre-releases are pushed to `main`. Anyone able to move `stable` (A5) can point it at one,
    or at any earlier signed commit, and machines accept it.
  - ADR-028 says `show | compare` "shows the version". It shows dates only.
- **Scenario:** the owner tags `v0.1.2`, a fix for 0.1.x, after `v0.2.0`. Every machine on `stable`
  goes back to 0.1.x at its next `request system update`, and the comparison calls it newer.
- **Verified:** by reading (release.yml lines 95-105, pkg.rs `lock_moves`).
- **Fix:**
  - In CI, refuse unless `$TAG` is a higher version than the one `stable` has, and is not a
    pre-release.
  - Put the version in the signed tree (it is in `cli/Cargo.toml`). torqcli compares versions, not
    dates, refuses an older one or a pre-release on `stable` unless the person confirms, and shows
    the version in `show | compare`.

### A4 — medium — a failed switch at first-boot setup is still ledgered as change #1, which can lock the machine out
- **Where:** `broker/src/lib.rs:657-668` (`set_up`), `modules/setup.nix:81`, `cli/src/setup.rs:164`.
- **What is wrong:** `set_up` writes the `init` entry whether or not `rebuild` succeeded. Its comment
  reasons that a switch sets the boot default before activating, but not every failure gets that far.
  - `nix-env --set` can fail.
  - `switch-to-configuration` installs the boot loader first and stops if that fails. The image has
    `canTouchEfiVariables = true`, and EFI variable writes are a known failure on some firmware.
  Either way, the image's system stays running and stays the boot default, while the ledger is no
  longer empty.
- **Scenario:**
  1. Setup says "TorqOS is set up … Log in as alice" and starts a getty. alice does not exist:
     `mutableUsers = false`, and the image declares no person.
  2. After a reboot the image starts again. `torq-setup` is skipped because the ledger is not empty,
     and the boot-menu editor is off.
  3. Nobody can log in. The way back is rescue media or a reinstall.
- **Verified:** by reading, and by the broker's own unit test, which asserts this behaviour
  (`broker/tests/trust_loop.rs:2141-2146`: a rebuild of `false`, ledgered as "TorqOS set up (the
  switch reported a problem…)").
- **Fix:** ledger change #1 only if the new system is the running system or the boot default.
  Otherwise handle it as the build-failure path does: remove the history and setup.json, and setup
  starts over. Add the case to the test.

### A5 — medium — release authority is wider than the release key (CI)
- **Where:** `.github/workflows/bump.yml:25-31`, `.github/workflows/release.yml` (no `environment:`,
  no check on where the tag points).
- **What is wrong:**
  - **The token is everywhere.** `TORQOS_RELEASES_TOKEN` is set in bump's job-level env, so every
    step sees it, including `cachix/install-nix-action@v31`, which is pinned by tag. `actions/checkout`
    also stores it in `.git/config`.
  - **It is a release capability.** That token can push to this repo (ADR-028). Pushing a `v*` tag on
    any commit, which need not be on `main` or touch a workflow, makes release.yml test it, build it,
    sign it with the real key and move `stable`.
  - **No gate.** The key is a plain repository secret, with no protected environment and no required
    reviewer.
- **Scenario:** an upstream action pinned by tag is compromised. It reads the token from bump's
  environment, pushes a branch and a `v9.9.9` tag, and CI signs and publishes it to every machine.
- **Verified:** by reading. GitHub's repository settings (tag rulesets, environments) were not
  checked.
- **Fix:**
  - Put the key and the releases token in a `release` environment limited to `v*` tags, with a
    required reviewer.
  - Give bump its own token, scoped to PRs and set in the step's env only.
  - In release.yml, require that the tag is signed by the owner and that `git merge-base
    --is-ancestor "$GITHUB_SHA" origin/main` holds.
  - Pin third-party actions by SHA.

### A6 — low — the release check fails open, without a word
- **Where:** `cli/src/session.rs:965`, `cli/src/software.rs:83-99`.
- **What is wrong:**
  - **Silently unchecked sources.** A lock whose `torq` input is not the releases repo, spelled
    exactly as normalised, is not checked, and nothing says so. That covers `github:netstacks/torqos`
    (the template's default and the error message's example), a fork, a tarball of the releases repo,
    and `git+https://www.github.com/…`.
  - **`github:` is accepted as the releases repo,** but Nix builds GitHub's tarball, whose bytes the
    `rev` does not bind, so ADR-028's "exactly the commit checked" holds only for `git+`.
- **Scenario:** a person sets the source to a fork, or to a URL spelled differently, and believes it
  is checked.
- **Verified:** by reading.
- **Fix:**
  - Fail closed: require the release key's signature unless the source is a dev-mode `path:` or the
    image's own store path.
  - At the least, print "not checked against the TorqOS release key" in the comparison and the commit
    question.
  - Accept the releases only as `git`.

### A7 — low — the fence: the broker's units can be removed by three spellings it does not know
- **Where:** `modules/settings-fence.nix:37-54` (patterns), `modules/setup.nix:63-68`, README.md:246-248.
- **What is wrong:** the fence refuses `systemd.services/timers/units."torq-*"` and `torq.installer`,
  but three other spellings switch off the broker's own units:
  1. `nixos/systemd.json` with `{"suppressedSystemUnits": ["torq-status.service",
     "torq-status.timer", "torq-confirm-boot.service"]}`. It evaluates with no failed assertion, and
     the built `system-units` contain only `torq-broker-init.service`.
  2. `nixos/boot.json` with `{"kernelParams": ["systemd.mask=torq-status.timer", …]}`. It evaluates;
     systemd masks those units at boot (systemd-debug-generator).
  3. `nixos/torq.json` with `{"user": null, "setup": {"enable": true, "source": {…}}}`. `torq.setup`
     is not fenced. This evaluates with no failed assertion, with `torq-status` and
     `torq-broker-init` off and `torq-setup` defined. It is the same class as `torq.installer`, which
     was fenced on 2026-11-03.

  What is lost is the passive drift check: the boot and 15-minute check, the login warning, and the
  ledgering of a rollback by reboot. `show system alarms` asks the broker directly, so drift is still
  found when someone asks. Each of these is a system-tier change shown to the person, which is the
  power 6m concedes. The README's "its units … refused … however they are spelled" is what is false.
- **Verified:** yes, with `nix eval` and builds of `system-units` (`scratchpad/main/eval.nix`,
  `cases/`). An `/etc` entry nested under `systemd/system/…` was also tried, and it did **not**
  override a unit.
- **Fix:**
  - Fence `torq.setup`.
  - Add a TorqOS assertion on the evaluated system: no `torq-*` unit in `systemd.suppressedSystemUnits`,
    and no `systemd.mask=`/`systemd.wants=` naming one in `boot.kernelParams`. This checks what they
    become, as security.nix does for /etc.
  - Add the three as tree cases.
  - Or reword the README to the fence's own header: data only; root-code settings are system-tier.

### A8 — low — the installer: a complete, bootable disk without its hardware file, for longer than conceded
- **Where:** `cli/src/install.rs:556` (read-back), `:604-606` (the partition table written), `:647-684`
  (settle, then detection); `cli/src/setup.rs:108-110`.
- **What is wrong:** the partition table is written before the read-back, the waits on udev, and the
  hardware detection. A power cut or reset anywhere in that window, which lasts as long as the whole
  write, leaves a disk that boots without the detected hardware file. If it comes during the
  read-back, the bytes were never checked either. Setup then silently takes the image's VM hardware
  file. KNOWN-GAPS 6zc concedes only the seconds before the first MiB, on a disk exactly the image's
  size.
- **Verified:** by reading (installer reviewer).
- **Fix:** write the first MiB only after the read-back and the hardware file (mount the root through
  a loop device at the image's partition offset on the open disk), or detect the hardware before
  writing, as 6zc suggests. Setup should say when it falls back to the image's hardware file.

### A9 — low — an interrupted setup leaves the password file of the name it was given
- **Where:** `cli/src/setup.rs:254-255` (written before the broker runs), `:173-174` and `:186` (only
  the in-process error removes it).
- **What is wrong:** a power cut mid-build leaves `/var/lib/torq/secrets/passwords/<first name>`.
  - **Scenario:** the next setup is answered with another name. Later, `isNormalUser` for the first
    name points that account at the old file (`accounts.nix:19`), and it gets the password typed in
    the aborted setup. It was typed by the owner, which is why this is low.
- **Verified:** by reading.
- **Fix:** empty the passwords folder at the top of each setup attempt. Before change #1 nothing else
  owns it.

### A10 — low — Ctrl-C at a setup question ends setup until the next boot
- **Where:** `modules/setup.nix:94` (`Restart=on-failure`), `cli/src/setup.rs`.
- **What is wrong:** setup leaves the console's signal keys on, unlike the installer, and systemd
  counts death by SIGINT as a clean exit, so the unit is not restarted. The console is left with
  neither setup nor an account.
- **Verified:** reasoned from systemd.service(5), not run.
- **Fix:** `Restart=always`, or clear ISIG as `install.rs:335-337` does.

### A11 — low — release hygiene
- **Where:** `.github/workflows/release.yml:95`, `:102-106`, `:120`; release/allowed_signers.
- **What is wrong:**
  - **A moved tag is signed untested.** The source is archived from `"$TAG"` at publish time, hours
    after the tests, so a tag moved meanwhile is signed without being tested. Use `$GITHUB_SHA` and
    assert the tag still names it.
  - **Loose pre-release detection.** The pattern is `*-*`, so `v1.2.0rc1`, `v1.2.0+x` and `vfoo`
    count as stable releases.
  - **No revocation.** There is no revocation file and no `valid-before`: a leaked key stays trusted,
    and can itself sign the update that would replace it. Add `gpg.ssh.revocationFile` (empty, in
    /etc/torq) now, while the check is rewritten (A1).
  - **The fingerprint has one home.** It is checked against the release notes, which live in the
    same place as the downloads.
- **Verified:** by reading.

### A12 — low (documents) — claims stronger than the code
- **README.md:250, "`torq-broker verify` detects any change to it."** It does not detect truncation
  of the newest entries, and root can rewrite the chain consistently (KNOWN-GAPS #2). Say "any edited,
  added or removed entry inside the chain".
- **SECURITY-MODEL.md:82, "A machine updates only to a commit signed with the key it was installed
  with."** False, because of A1, A2 and A6.
- **SECURITY-MODEL.md:128, "signed modules only".** Not true (KNOWN-GAPS 6).
- **SECURITY-MODEL.md:130, "all TorqOS services use systemd sandboxing".** Not true (N5, open). Only
  `torq-broker-init` has any.
- **SECURITY-MODEL.md:131, "allowed-users restricted; only the broker may trigger system rebuilds".**
  `allowed-users` is `root @wheel` (`modules/base.nix:38`), so wheel users can build anything, and
  root can switch by hand (conceded in CLAUDE.md).
- **ADR-028, "`show | compare` shows the version".** It shows dates (A3).

### Checked, and not holes
- **Broker settings and environment.** A root broker refuses flags and `TORQ_*` variables that
  differ from broker.json. Children get `env_clear`, `/`, umask 022, and no global or system git
  config, hooks or fsmonitor. Every build is `git+file://<repo>?rev=<ledgered commit>`, with
  `--no-update-lock-file`.
- **What Nix builds is what git committed.** Nix 2.34 does not honour `export-ignore` for
  `git+file`, so a `.gitattributes` cannot make it differ from what torqcli shows (tested).
- **The switch and the lock.** The transient `torq-switch` unit inherits the broker lock through
  stdin (`--pipe`), and `switch_running` guards every operation that changes the machine.
- **Tiers.** They are computed from what the diff does (a scratch index, `--no-renames`), not from
  its headers. User-tier content is shape-checked and must be mode 100644. `git apply` refuses `.git/`
  and paths beyond a symlink.
- **Commit confirmed.** The rollback uses the anchor system's own commands. A reboot rolls back by
  construction, since the boot default is unchanged until `confirm`.
- **Passwords.** A person's password reaches no argv, environment, log, the repo, the store or the
  ledger. Files are made with 0600 `create_new` in a 0700 folder. Root and a person with a
  non-default password file are kept out of `torq.accounts.people`.
- **The installer's disk choice.** It lists whole disks only, takes the choice by number and the
  confirmation by name, and opens the disk O_EXCL with device number, diskseq and size re-checked,
  later opens included. No hole was found in it.
- **The release check's isolation.** It runs in a fresh 0700 folder, fetched from the trusted URL,
  never the lock's, with no `GIT_*`, global or system config.
- **The release trust root is fenced from the tree.** It is not fenced from attached `.nix` files,
  which 6m concedes.
